# 答辩演示提纲

> 建议时长：3 分钟精简版 / 5 分钟标准版 / 8—10 分钟完整版。  
> 演示前先启动：`scripts\start-server.bat`，浏览器打开 `http://localhost:8080/campus-trade-admin/`。

## 一、30 秒项目介绍

“这是一个校园二手交易平台的后台管理系统，采用 Java EE 的 Servlet + JSP + JDBC + MySQL 分层架构。它解决三个问题：商品先审后发、订单全程可追溯、举报处理能联动下架商品/封禁用户/扣信用分。所有关键操作都会写入审核日志。”

技术栈一句话：

“前端是 JSP + JSTL + 原生 CSS/JS，后端是 Servlet + Service + DAO，数据库 MySQL 8，连接池 Druid，构建 Maven，部署在 Tomcat 11。”

## 三、5 分钟标准演示

### 1. 登录与看板（40 秒）

- 说明管理员账号来自 `t_user`，密码用 PBKDF2 存储，不是明文/MD5。
- 登录成功后 `LoginServlet` 销毁旧 Session，防止会话固定。
- 看板统计来自 `DashboardService`：用户数、商品数、订单数、成交额、待审核、待举报、解决率。
- 近 7 天订单趋势由 `OrderDao.trend()` 按日期分组，Java 补齐缺失日期。

### 2. 商品审核（60 秒）

- 打开待审核商品“高等数学同济第七版”。
- 讲状态机：`PENDING → APPROVED / REJECTED`。
- 驳回必须填原因；通过后写 `audit_by/audit_time`。
- 审核和日志在同一个事务里，避免“状态改了但日志没写”。
- 批量通过：只处理 `PENDING`，其他状态自动跳过。

### 3. 举报处理（80 秒）

- 打开举报 #1（化妆品小样，原因“虚假描述”）。
- 展示举报对象快照：商品标题、卖家、价格、状态。
- 选择“举报成立 + 下架商品”，填写处理说明。
- 提交后：
  - `t_report.status = RESOLVED`
  - `t_product.status = OFF_SHELF`
  - 写举报日志 + 商品下架日志
- 说明还可选“封禁用户”“警告扣 5 分”，都是同一事务。
- 这是本项目的特色：举报不是孤立标记，而是业务联动。

### 4. 订单管理（60 秒）

- 打开订单 `CT202610290002`（自行车，待收货）。
- 展示买家/卖家、交付方式、地址、时间线。
- 流转为“已完成”，写入 `finish_time` 和审核日志。
- 讲状态机：待付款 → 待发货 → 待收货 → 已完成；旁路有取消/退款。
- 前端只展示允许的下一步，后端 Service 再校验一次，防止伪造参数。

### 5. 用户、分类、日志（40 秒）

- 用户详情：信用分、发布商品、订单、举报记录；封禁/解封/重置密码。
- 分类：新增、编辑、停用、删除保护。
- 日志：按业务类型/动作筛选，所有关键操作可追溯。

### 6. 导出（20 秒）

- 订单/举报导出 Excel，使用 Apache POI，带表头样式、冻结首行、自动列宽。

## 四、8—10 分钟完整演示（可选）

在 5 分钟基础上增加：

1. **数据库 ER 图**：讲 6 张表、外键、索引。
2. **登录链路**：浏览器 → EncodingFilter → LoginServlet → AuthService → UserDao → Session → AuthFilter → JSP。
3. **事务演示**：举报处理时同时改举报、商品、日志；如果中途失败会回滚。
4. **安全设计**：PreparedStatement、PBKDF2、`c:out`、Session 固定、JSP 放 WEB-INF。
5. **扩展功能**：公告管理、图片上传、前台用户端、通知中心。
6. **部署**：Maven 打 WAR，Tomcat 11 部署，MySQL 自动初始化。

## 五、答辩常见问题与参考回答

### Q1：为什么不用 Spring Boot？

“课程要求是 Java EE / Java Web，我想把 Servlet 生命周期、Filter 链、Session、JDBC、事务这些基础打牢。这个项目没有用 Spring，所有分层和事务都是自己写的，答辩时每一行都能讲清楚。以后如果要工程化，可以平滑迁移到 Spring Boot。”

### Q2：为什么商品要“先审后发”？

“校园二手交易容易出现违规电器、假冒化妆品、虚假描述、站外引流等问题。先审后发可以在商品进入前台之前拦截，降低交易纠纷和平台风险。审核记录也会写入日志，便于追责。”

### Q3：举报处理为什么要用事务？

“因为一次处理可能同时改三张表：举报状态、商品状态/用户状态、审核日志。如果只成功一半，会出现‘举报显示已处理，但商品还在卖’的不一致。`DbUtil.inTransaction` 保证要么全部成功，要么全部回滚。”

### Q4：怎么防止 SQL 注入？

“所有 SQL 都用 `PreparedStatement` 的 `?` 占位符，用户输入只作为参数传入，不拼接到 SQL 字符串。动态筛选也是用 `StringBuilder` 拼条件、参数放到 `List` 里，值仍然走占位符。”

### Q5：密码为什么不用 MD5？

“MD5 太快、无盐、可被彩虹表撞库。项目用 PBKDF2-HMAC-SHA256，12 万次迭代，每个用户 16 字节随机盐，格式是 `pbkdf2$迭代$盐$摘要`。校验时用 `MessageDigest.isEqual` 做常量时间比较。”

### Q6：怎么防止用户直接访问后台 JSP？

“JSP 都放在 `WEB-INF/views` 下，Servlet 容器不允许浏览器直接访问 WEB-INF。所有 `/admin/*` 请求还要经过 `AuthFilter`，未登录跳登录页，非管理员返回 403。”

### Q7：订单状态机怎么保证不被乱改？

“`OrderService.nextStatuses()` 根据当前状态给出允许的下一步，前端只展示这些选项；Service 在更新前再校验一次，目标状态不在允许列表就抛 `BizException`。所以就算用户改 HTTP 参数也没用。”

### Q8：举报对象有商品、订单、用户三种，怎么关联？

“`t_report` 用 `target_type + target_id` 做多态关联，不建三个外键。详情页由 `ReportService.targetInfo()` 根据类型分别查商品/订单/用户，拼成对象快照。处理时再由 `resolveProductId()` / `resolveUserId()` 找到要处罚的对象。”

### Q9：如果两个人同时审核同一件商品怎么办？

“当前是课程项目，用‘状态必须为 PENDING’做基本校验，能挡住绝大多数重复操作。更高并发下可以加乐观锁，比如 `UPDATE ... WHERE id=? AND status='PENDING'`，根据受影响行数判断是否抢到审核权；或者用 `SELECT ... FOR UPDATE`。”

### Q10：项目的亮点是什么？

“三个亮点：
1. 举报处理不是简单改状态，而是联动下架商品/封禁用户/扣信用分，并且全过程事务 + 日志。
2. 订单有完整状态机和节点时间戳，前端选项和后端校验双层约束。
3. 纯 Java EE 手写分层，配合本地 SVG、响应式 UI 和 Excel 导出，功能完整且不依赖外网。”

### Q11：如果让你继续加功能，你会加什么？

“优先加：前台用户端（发布/下单/举报入口）、图片上传、审核结果通知、修改密码、角色细分（审核员/客服）、CSRF Token 和登录失败限制。数据量大之后再看 Redis 缓存和列表索引优化。”

### Q12：数据库为什么这样设计？

“用户和商品、订单、举报、日志分开，避免一张大表。订单同时冗余 `product_id/buyer_id/seller_id`，是为了查询和追溯；金额用 `DECIMAL`；状态用字符串便于阅读和扩展；关键查询建了组合索引。”
